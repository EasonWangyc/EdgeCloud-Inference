# 数据集与 LoRA 优化方案

## 当前证据

现有 `ps80_human_confirmed_v1` 含 80 个样本，其中训练集 64 个、验证集 16 个；当前 manifest 中每个样本有独立 `source_group_id`。独立来源组数量与样本数相同，说明当前版本尚未证明连续帧、相邻采集或同一场景已按真实来源归并。后续应先核对图片来源，并将同一视频、采集序列或场景的样本合并到同一个来源组，再重新执行分组切分。

| 划分 | 样本 | 风险等级 | 各风险事件正例数 |
| --- | ---: | --- | --- |
| train | 64 | low 35，medium 26，high 3 | vehicle 20，narrow 18，visibility 7，fixed obstacle 1，VRU 1，parking conflict 0 |
| validation | 16 | low 10，medium 6，high 0 | vehicle 3，narrow 3，visibility 3，fixed obstacle 1，VRU 0，parking conflict 0 |

数据量和分布都不足以稳定判断稀有事件。验证集中 `fixed_obstacle_near_path` 只有 1 个正例，VRU 和车位冲突没有正例；高风险也没有样本。当前验证分数的变化可能来自少数样本，不能据此断言某个训练改动稳定有效。

已保存的 Transformers 服务器研究结果：

| 运行 / 数据 | n | JSON 有效率 | 风险等级准确率 | 事件 micro-F1 | 不安全建议率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| base，PS20 pilot | 20 | 1.000 | 0.350 | 0.350 | 0.000 |
| reviewed v1，PS20 pilot | 20 | 1.000 | 0.600 | 0.200 | 0.000 |
| reviewed v2 semantic，PS80 validation | 16 | 1.000 | 0.563 | 0.429 | 0.000 |
| reviewed v3 calibration-aligned，PS80 validation | 16 | 1.000 | 0.563 | 0.429 | 0.000 |
| reviewed v4 event-focus，PS80 validation | 16 | 1.000 | 0.375 | 0.353 | 0.000 |

v2 到 v3 在当前 16 个验证样本上没有指标变化；v4 的事件 focus 配置使风险准确率和事件 micro-F1 都下降。v4 记录的主要事件错误为 `vehicle_near_maneuver_path` 与 `narrow_passage` 各 9 个 false positive，`visibility_occlusion` 有 3 个 false negative，`fixed_obstacle_near_path` 有 1 个 false negative。JSON 有效率为 1 只说明 schema 可解析，不代表识别质量足够。

PS20 pilot 仅 20 个样本，适合作为固定冒烟/回归集，不足以承担微调选型或最终泛化结论。PS80 validation 已经被多轮训练和方案比较使用，应继续作为开发集，不应改称独立测试集。以上分数来自报告文件中的服务器 Transformers 执行，不是 vLLM 或 Jetson TensorRT 的质量/性能结果。

## 阶段 0：冻结当前数据与复核来源

1. 保留 `ps80_human_confirmed_v1`、既有 PS20 pilot 和报告原样不改，核对原始图片、采集序列、近重复图片及来源元数据。
2. 为同一视频、连续帧、同一停车位/车辆连拍等关联样本填写同一 `source_group_id`。通过近重复检查及人工来源核验后，按来源组重切 train、development、test；不允许同组跨集合。
3. 从数据卡补齐授权/隐私状态、采集环境、相机视角、图像质量、标注者和裁决记录。无法确认数据使用权限或来源的样本不得进入训练或测试。
4. 将 PS20 和现有 PS80 继续用作历史可比集；新建版本化的分组测试集，创建后锁定其图片、标注、manifest 和 workload 哈希。

## 阶段 1：扩充并规范标注

先按稀有事件和易混淆决策采集，而不是继续堆积容易的 low/无事件样本。采样清单至少覆盖：行人/骑行者进入机动路径、固定障碍、窄通道与普通近车的边界、车位冲突、遮挡/低照度/雨天/反光，以及“目标在画面中但不在机动路径”的 hard negative。六类事件均需要正例和相近负例；同时补齐 high 风险样本及风险等级边界案例。

标注采用书面决策规则：目标是否靠近自车机动路径、可见证据在哪里、风险等级如何由事件和可见性决定、建议动作是否安全。新标签记录 `label_source`、标注者、复核者和裁决状态。所有稀有类别、边界案例和测试集样本由第二人复核；分歧先裁决再锁定。模型/教师生成标签只可作为待审候选，不能因结构合法自动成为金标。

数据增长采用两步门槛：先新增并人工确认一批约 120–200 个有针对性的样本，重点填补当前零/单例类别；之后依据来源组级验证结果和错误样例决定是否扩展到约 300–500 个总样本。数量是采集规划值，不是效果保证。进入正式微调前，development 和 test 中每个事件都应有足以分析的独立来源组正例；稀有事件不足时标记“证据不足”，不汇总成确定性结论。可将每个事件至少 20 个 development 正例组、30 个 test 正例组作为启动评测的下限目标，实际数量和置信区间同时报告。

建议按来源组约 70/15/15 切分 train/development/test，并对稀有事件做分层约束；只有在组级去重后才执行分配。若现有数据不足以满足某类分层，不应拆散来源组，应继续收集该类数据。测试集在训练配方、prompt、阈值、量化校准方案确定前冻结。

## 阶段 2：微调配方对照

所有实验使用相同基础模型 revision、冻结 workload、训练样本、图像预处理、生成参数和随机种子。先复现 base 与现有 reviewed v3/v4，再一次只改变一个变量：

1. **基线复现**：无 LoRA 的 base、reviewed v3、reviewed v4，在同一 development 集上重跑并逐样本对齐，确认现有差异可重现。
2. **标签与目标**：使用经复核的 `ParkingAssessment` 标签；检查文本答案中证据、事件和建议是否彼此一致。初期保留现有 q/k/v/o、rank 16 配方，避免同时改变数据、LoRA rank 和 prompt。
3. **采样对照**：比较不重采样、温和的风险等级加权、基于多标签事件频次的 sampler。现有配置对 non-low 过采样 2 倍、事件过采样 3 倍，v4 在小验证集上退化；不将过采样倍数继续加大作为默认方案。每轮保存真实曝光频次，避免多标签样本被重复放大。
4. **优化强度**：在数据和采样固定后，再对学习率、epoch 与 warmup 做小范围单变量对照；优先减少过拟合风险，保留 early checkpoint 并只用 development 选择。确定配方后使用 3 个随机种子复核稳定性。
5. **增强数据**：可评估保持语义的轻微亮度、对比度和模糊扰动；增强版本仅进入训练。不得通过翻转/裁切等改变车辆位置、左右关系、目标与机动路径关系或遮挡判断的变换来伪造标签。

微调期间同时记录 train/development loss、每类 precision/recall、预测事件频率、风险混淆矩阵、建议安全错误和来源组级错误案例。根据误报/漏报回到数据或标注规则定位原因，不以总体 loss 或 JSON 有效率单独选择 checkpoint。

## 阶段 3：评测和晋级门槛

- 开发阶段：在 development 上做配方选择，报告风险准确率、macro-F1、事件 micro/macro-F1、每类 TP/FP/FN、严重风险漏报、不安全建议率和 JSON 有效率。
- 冻结测试：仅对选定的 base 与候选 adapter 做一次预注册对照；按 `source_group_id` 配对 bootstrap 置信区间，并公布样本/正例组数。禁止在看过测试错误后再改模型并继续把同一集合称为独立测试。
- 质量门槛：JSON schema 通过率达到 100%；不安全建议和 high 风险漏报逐例审查；候选至少在主要风险与事件指标上优于 base，且关键事件不出现无法接受的回归。样本量不足以支持结论时继续扩充测试来源组，不用单点百分比宣称提升。
- 迁移部署：服务器 Transformers 先确认模型/adapter 的任务正确性；之后分别做 vLLM 和 Jetson TensorRT 的同一冻结数据质量对照。量化版本另行报告质量变化，不把云端时延和板端时延混作性能结论。

## 运行记录与产物

每次训练配置固定并归档：基础模型 revision、数据/标注/manifest 哈希、source-group split、标签来源、workload 哈希、种子、采样曝光、LoRA 配置、优化器参数、训练环境、checkpoint、合并版本和评测报告。候选数据与人工确认数据使用独立文件名；不得覆盖已冻结的 manifest、annotations 或报告。

当前推荐顺序为：先完成云端 vLLM 与端云路由的可运行链路，再执行阶段 0 的来源审计和测试集冻结，随后扩充稀有事件、开展配方对照。新 adapter 在数据和独立测试证据到位前保持候选状态。
